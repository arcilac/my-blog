API Rate limiting

APIs are highways. Some cars (requests) drive normally, some speed, and some try to flood the road. Without a traffic cop, chaos follows: servers crash, data leaks, and everyone has a bad time.

That's where rate limiting comes in: the rulebook that decides "how many requests a user can make and how fast."

🎭 What is rate limiting?

Simple answer: A rule that limits how many requests you can make in a given time window.

Real answer: A protection mechanism that prevents abuse, keeps APIs stable, and ensures fair usage.

Think of it like a club bouncer:

User → Tries to enter 20 times in 5 seconds → Bouncer says "too many, wait outside."

⚡ Common strategies

1. Fixed Window Limit requests per time window (e.g., 100 requests per minute).

// Pseudo-example
if (requests[user] > 100 in 60s) {
  block(user);
}

✅ Simple, easy to implement

❌ Can allow bursts (100 requests in the last second of the minute)

2. Sliding Window More precise — checks requests in the last _N_ seconds.

Request log → Look back 60s → If >100, block

✅ Smoother distribution

❌ More memory overhead (tracking timestamps)

3. Token Bucket Users get "tokens" they spend per request. Tokens refill at a rate (e.g., 1 per second).

// 10 tokens max, refill 1/s
if (tokens[user] > 0) {
  tokens[user]--;
  allow();
} else {
  block();
}

✅ Flexible, handles bursts gracefully

❌ Slightly more complex

4. Leaky Bucket Requests are queued and processed at a fixed rate. Extra requests overflow (rejected).

Think of it as: A funnel dripping water at a steady pace.

🎯 Real implementation examples

Express.js with express-rate-limit

import rateLimit from "express-rate-limit";

const limiter = rateLimit({
  windowMs: 60 * 1000, // 1 minute
  max: 100, // 100 requests per minute
  message: { error: "Too many requests, slow down 🚦" },
});

app.use("/api", limiter);

Nginx (Reverse Proxy)

limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;

server {
  location /api/ {
    limit_req zone=api burst=20 nodelay;
  }
}

Redis-based Distributed Limiting When you have multiple servers, store counters in Redis for consistency.

INCR user:123:requests
EXPIRE user:123:requests 60

🚨 When rate limiting goes wrong

  • Too strict: Users get blocked during normal usage
  • Too loose: Attackers can still flood your API
  • Inconsistent across servers: Without shared state (like Redis), limits break in distributed systems
  • Poor UX: No clear error messages, leaving users confused

👉 Always return HTTP 429 (Too Many Requests) with helpful headers:

HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-RateLimit-Remaining: 0

🔥 Pro tips for mastery

  • Use different limits per route (/auth/login stricter than /products)
  • Combine rate limiting + caching to handle traffic spikes
  • Expose headers like X-RateLimit-Remaining so clients know their quota
  • Add graceful degradation (slow down instead of hard-block)
  • Monitor logs to detect real abuse vs false positives

🚀 The bottom line

Rate limiting is your traffic cop. It prevents chaos, protects servers, and makes APIs fair for everyone.

The mindset:

  • Keep it simple but effective
  • Use the right algorithm for your needs
  • Communicate limits clearly with users
  • Always think distributed (cloud, microservices)

Without it, your API is a highway with no speed limit — fun for attackers, but a nightmare for everyone else. 🚦

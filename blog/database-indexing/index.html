Database indexing

Databases are like libraries. Without indexes, finding a book means scanning every shelf, every row, every book. With an index, you jump straight to the right section.

That's exactly what indexing does: it makes lookups faster by creating a map for your queries.

📚 What's a database index?

An index is an extra data structure (usually a B-Tree or Hash) that helps the database find rows without scanning the entire table.

Think of it like:

Without index → Read every row until you find "Pedro"
With index    → Jump straight to where "Pedro" is stored

Indexes come with trade-offs: they take extra space and slow down writes (because the index must update every time you insert/update/delete).

⚡ Why indexing matters

Let's compare performance:

-- Without index
SELECT * FROM users WHERE email = 'maria@example.com';
-- → Full Table Scan: 10M rows ~30 seconds

-- With index on email
CREATE INDEX idx_users_email ON users(email);

SELECT * FROM users WHERE email = 'maria@example.com';
-- → Index Scan: ~0.003 seconds

A single index can turn a query from seconds → milliseconds.

🎯 Types of indexes

1. Single-Column Index

CREATE INDEX idx_users_email ON users(email);

2. Composite Index Covers multiple columns (order matters - database reads left-to-right).

CREATE INDEX idx_orders_user_date ON orders(user_id, created_at);

👉 Works for (user_id, created_at) but not for created_at alone.

3. Covering Index Includes all columns the query needs, avoiding table lookups.

CREATE INDEX idx_users_covering
ON users(email) INCLUDE (name, created_at);

4. Unique Index

CREATE UNIQUE INDEX idx_users_username ON users(username);

5. Full-Text Index

CREATE FULLTEXT INDEX idx_posts_body ON posts(body);
SELECT * FROM posts WHERE MATCH(body) AGAINST('database');

6. Partial Index

CREATE INDEX idx_active_users ON users(email) WHERE active = true;

🚨 When indexing goes wrong

  • Over-Indexing: Too many indexes slow down writes
  • Wrong Order: (a, b) ≠ (b, a) for composite indexes
  • Low Selectivity: Indexing true/false columns is usually useless
  • Unused Indexes: Monitor with EXPLAIN and remove dead weight

🔥 Case study: bad vs good

Bad:

-- 50% of rows are active = too many results
SELECT * FROM users WHERE is_active = true;

Good:

CREATE INDEX idx_users_active_email ON users(is_active, email);

SELECT * FROM users
WHERE is_active = true AND email = 'maria@example.com';
-- → Highly selective: query flies

🎯 Pro tips

  • 🔹 Index for queries, not columns — start from slow queries
  • 🔹 Use EXPLAIN to verify index usage
  • 🔹 High-cardinality columns benefit most (emails > status flags)
  • 🔹 Monitor unused indexes — they waste space and slow writes

🚀 The bottom line

Indexes are shortcuts: they don't change your data, only how fast you can find it.

  • Without them → database reads every row
  • With them → database jumps directly to what you need

But remember: every shortcut has a cost. Index smart, not blindly.

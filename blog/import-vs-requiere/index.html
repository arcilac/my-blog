Import vs require: what’s the difference and why it matters

If you’ve written JavaScript long enough, you’ve probably seen both:

const fs = require('fs'); // CommonJS
import fs from 'fs';      // ES Modules

At first glance, they seem to do the same thing: bring code into your file.

But behind the scenes, they represent two different module systems — and choosing one over the other can affect your app’s performance, compatibility, and future scalability.

Let’s unpack this.

🔄 The two module systems

Featurerequire()import
Module SystemCommonJSES Modules (ESM)
Loading StyleSynchronous (blocking)Asynchronous (non-blocking)
When AvailableNode.js (default before ESM)Native in browsers & modern tools
SyntaxDynamicStatic
Tree-shakable❌ No✅ Yes

🧠 Require(): CommonJS

Used mainly in Node.js, require() loads modules at runtime, meaning the code runs line by line and fetches dependencies as it encounters them.

const lodash = require('lodash');

✅ Pros:

  • Works out of the box in Node.js.
  • Supports dynamic imports (e.g. require(someVariable)).

❌ Cons:

  • Not tree-shakable (can include unused code).
  • Not natively supported in browsers.
  • Blocks execution while loading — bad for performance in large codebases.

🚀 Import: ES Modules (ESM)

Introduced in ES6, import is now the standard way to manage modules in modern JavaScript — both in browsers and tools like Webpack, Vite, and Rollup.

import { uniq } from 'lodash';

✅ Pros:

  • Native browser support (no bundler needed in many cases).
  • Async and non-blocking — better for performance.
  • Fully tree-shakable — only the used code is included.
  • Cleaner syntax for modern tooling and TypeScript.

❌ Cons:

  • Slightly more complex setup in Node.js (requires type: "module" in package.json).
  • No dynamic import unless using import() (which returns a promise).

📈 Why it matters to users

Users don’t see your code — but they experience its impact.

Choosing import over require enables:

  • ⚡ Smaller bundles (thanks to tree-shaking)
  • 🚀 Faster loading apps
  • 🌍 Better cross-platform compatibility
  • 🔧 Easier debugging and maintainability in modern projects

Especially when building frontend apps, import is the clear winner.

🔄 Mixing both?

Yes, you can use both in some Node.js setups, but it’s messy and error-prone.

Example:

// Mixing styles – not recommended
const utils = require('./utils.mjs'); // May throw error if not configured

Modern projects should stick to one: ideally, ES Modules (import).

🛠 When to use what

Use CaseUse requireUse import
Legacy Node.js scripts✅❌ (not supported)
Frontend apps with Webpack/Vite❌✅
Isomorphic/Universal apps❌ (less portable)✅ (preferred)
Modern Node.js with ESM setup❌ (outdated)✅ (native)

🧪 Conclusion

  • require() is the old Node.js way (CommonJS).
  • import is the modern, browser-native, async, tree-shakable standard.
  • Choose import for any new frontend or full-stack project.
  • Avoid mixing them unless absolutely necessary.
Modern JavaScript deserves modern tools.

Use import — your users (and future self) will thank you.
